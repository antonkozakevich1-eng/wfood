# WFOOD — Архитектура (ЭТАП 1)

> Пилот: **Эстония, Таллинн, валюта EUR (€)**. Языки интерфейса: RU (основной), EN.
> Цель продукта: ответ на вопрос «Где поесть?» за 10 секунд.

---

## 1. Ключевые решения и их обоснование

### 1.1. Источники данных о местах — инвертированный приоритет для Эстонии

В исходном ТЗ первым источником стоял Google Places API. Для Таллинна это меняется:

| Источник | Роль в WFOOD | Почему так |
|---|---|---|
| **Overpass API (OpenStreetMap)** | **Основной, бесплатный** | В Таллинне OSM-покрытие POI (`amenity=restaurant/cafe/bar/fast_food`) очень плотное, включая часы работы (`opening_hours`), кухню (`cuisine`), телефон, сайт. Не требует ключа и billing — приложение живёт с нулевым бюджетом. |
| **Google Places API** | Обогащение (опционально) | Лучшие фото, рейтинги, `price_level`, отзывы. Но: платный billing, обязателен ключ, квоты. Подключается флагом `PLACES_GOOGLE_ENABLED`, при отсутствии ключа просто выключается. |
| **2GIS API** | Не используется для Эстонии | Нет покрытия. Модуль оставлен в агрегаторе как расширяемая точка для РФ/СНГ (задел на «потом — глобально»). |
| **Краудсорсинг** | Пользовательские места | Позволяет закрывать дыры в покрытии и добавлять «свои» места (дворовые кафе, поп-апы). Пишутся в `places` с `source='crowd'` и проходят модерацию через RLS-политику. |
| **`src/data/tallinn-seed.ts`** | Оффлайн-фолбэк | Если Overpass недоступен (нет сети / rate limit), приложение показывает сид-набор реальных таллиннских заведений. Приложение **никогда не остаётся с пустым экраном**. |

**Trade-off:** OSM даёт меньше фото и рейтингов, чем Google. Компенсируем: (а) рейтинг считаем сами из избранного/выборов пользователя (`rating` nullable, UI показывает «Нет рейтинга»), (б) фото — карусель из `photos jsonb`, при пустом массиве показываем градиентный плейсхолдер с эмодзи категории, (в) DALL·E 3 генерирует обложки подборок и OG-картинки.

### 1.2. Слой мест: единый агрегатор с кэшем

```
useNearbyPlaces ──► lib/places.ts (агрегатор)
                        │
                        ├─1─► Supabase RPC nearby_places(lat,lng,radius,filters)
                        │        └─ таблица places (уже закэшированные, быстрые)
                        │
                        ├─2─► если пусто/устарело ──► Edge Function fetch-places
                        │        ├─ Overpass API  (primary, free)
                        │        ├─ Google Places (if key present)
                        │        └─ upsert в places + place_cache (TTL 7 дней)
                        │
                        └─3─► если Edge Function упала ──► tallinn-seed (локальный)
```

Правило: **клиент никогда не ходит в Overpass/Google напрямую.** Причины: (1) CORS и лимиты, (2) ключ Google Places нельзя отдавать в браузер, (3) агрегация + нормализация + upsert должны быть транзакционными.

### 1.3. Двойной ИИ: Gemini → OpenAI fallback

```
ChatWindow ──► lib/ai-client.ts ──► Edge Function ai-chat
                                        ├─ 1. Проверка суточного лимита (10 запросов/день, таблица ai_chats)
                                        ├─ 2. Кэш одинаковых запросов (hash от message+filters+geo-квадрат)
                                        ├─ 3. Gemini gemini-1.5-flash   ── успех ──► ответ
                                        └─ 4. ошибка/лимит/нет ключа ──► OpenAI gpt-4o-mini
                                                                          └─ ошибка ──►
                                        └─ 5. Оба упали ──► fallback-ответ-заглушка + результаты рулетки
```

**Почему ключи не на фронтенде:** Gemini принимает ключ в query-параметре URL, OpenAI — в заголовке. Любой из них в бандле = мгновенная утечка (Vite инлайнит `VITE_*` в JS открытым текстом). Оба ключа живут **только** в Supabase Secrets и читаются Edge Functions через `Deno.env.get()`.

**Почему формат ответа — JSON:** `{ reply, place_ids, reasoning }`. Это позволяет рисовать под ответом не текст, а **карточки реальных мест из выдачи** (`place_ids` → выборка из БД). Плюс это защита от галлюцинаций: модель физически не может показать место, которого нет — мы рендерим только то, что вернули из БД по id. Системный промпт явно запрещает выдумывать места.

### 1.4. Групповой режим (комнаты) — на Realtime, без поллинга

```
rooms + room_members + room_suggestions  ──► Supabase Realtime (postgres_changes)
```

Каждый участник пишет пожелание → оно пишется в `room_suggestions`. Когда все нажали «Готово» (или host жмёт «Собрать решение»), Edge Function `ai-chat` вызывается в режиме `room`: на вход уходят все пожелания + топ-30 мест, на выходе — общий компромиссный вариант. Realtime-подписка обновляет экран у всех без перезагрузки.

**Trade-off:** Realtime требует, чтобы таблицы были добавлены в publication `supabase_realtime` (сделано в миграции 002) и чтобы RLS не блокировал чтение — политики на `room_*` построены на членстве в комнате, а не на «свой-чужой», иначе участники не увидят чужие сообщения.

### 1.5. Лимит 10 бесплатных запросов/день

Считается **на сервере** (Edge Function), а не в localStorage — иначе лимит обходится очисткой кэша браузера. Счётчик = `count(*)` по `ai_chats` за текущие сутки по UTC. Отдельная таблица-счётчик не нужна: `ai_chats` и так пишет каждую пару запрос/ответ.

### 1.6. Состояние на клиенте (Zustand)

| Store | Что держит | Почему Zustand, а не Context |
|---|---|---|
| `authStore` | сессия Supabase, профиль | Сессия читается в 6+ местах; Context ререндерил бы всё дерево. |
| `filtersStore` | радиус, кухни, цена, тумблеры, сортировка | Изменение фильтра не должно ререндерить карту. Селекторные подписки Zustand это решают. |
| `placesStore` | список мест, кэш по ключу фильтров, избранное | Нужен кэш между вкладками + оптимистичное обновление избранного. |

Server-state отдельно не тащим (без React Query): данных мало, кэш — обычный `Map` по ключу «округлённые координаты + сериализованные фильтры».

### 1.7. Карта

Leaflet + `react-leaflet` + `leaflet.markercluster`. **Важно:** Leaflet требует `window`, поэтому нет SSR-проблем (у нас чистый SPA/Vite), но карту всё равно грузим лениво (`React.lazy`) — это ~150 КБ JS, который не нужен на вкладках Рулетка/ИИ. Тайлы OSM — бесплатные, attribution обязателен.

## 3. Границы доверия (важно для безопасности)

| Переменная | Где живёт | Префикс `VITE_` | Попадает в бандл |
|---|---|---|---|
| `SUPABASE_URL` | `.env.local` + Vercel | ✅ `VITE_` | Да — это публичный адрес |
| `SUPABASE_ANON_KEY` | `.env.local` + Vercel | ✅ `VITE_` | Да — он и создан для браузера, защита обеспечивается RLS |
| `SUPABASE_SERVICE_ROLE_KEY` | только Supabase Secrets / GitHub Secrets | ❌ | **Нет** — обходит RLS |
| `GEMINI_API_KEY` | только Supabase Secrets | ❌ | **Нет** |
| `OPENAI_API_KEY` | только Supabase Secrets | ❌ | **Нет** |
| `GOOGLE_PLACES_API_KEY` | только Supabase Secrets | ❌ | **Нет** |
| `OPENWEATHER_API_KEY` | только Supabase Secrets | ❌ | **Нет** |
| `VITE_POSTHOG_KEY` | `.env.local` + Vercel | ✅ `VITE_` | Да — публичный ingest-ключ |
| `VITE_DEFAULT_CITY` / `VITE_DEFAULT_CURRENCY` | `.env.local` + Vercel | ✅ `VITE_` | Да |
| `GITHUB_TOKEN` | только GitHub Secrets | ❌ | **Нет** |

Главное правило: **если переменная нужна Edge Function — у неё не должно быть префикса `VITE_`, и её не должно быть в Vercel Environment Variables.** И наоборот: фронтенд-переменные не нужны в Supabase Secrets.

## 4. Отказоустойчивость: что происходит, когда всё падает

| Что упало | Поведение приложения |
|---|---|
| Геолокация запрещена/недоступна | Центр карты → Таллинн (Raekoja plats), фильтр радиуса игнорируется, показываем баннер «Включите геолокацию» + кнопку «Выбрать район» |
| Overpass недоступен | Edge Function отдаёт то, что есть в `places`; если и там пусто — локальный `tallinn-seed` |
| Google Places ключ не задан | Модуль молча выключен, работаем на OSM |
| Gemini упал / лимит | OpenAI `gpt-4o-mini` |
| Gemini + OpenAI упали | Вежливое сообщение + локальные результаты рулетки без ИИ |
| DALL·E упал / ключа нет | Плейсхолдер-градиент, сгенерированный на CSS |
| Supabase целиком недоступен | Приложение работает в read-only режиме на сид-данных; избранное — в localStorage с очередью на синхронизацию |
| Нет сети (офлайн) | Service Worker: shell + последняя выдача мест из Cache Storage |

## 5. Почему PWA, а не нативное приложение

Целевая метрика — «10 секунд от открытия до ответа». Установка из App Store убивает воронку. PWA даёт: мгновенный вход по ссылке, добавление на домашний экран, офлайн-кэш, push (в задел). Цена — ограничения iOS (нельзя фоновая геолокация, ограниченный Storage API), поэтому офлайн-режим рассчитан на «последние N мест», а не на полноценную офлайн-базу.

## 6. Что осознанно не сделано (и почему)

- **Нет серверного рендеринга.** Vite SPA + Vercel rewrites. SSR дал бы SEO для страниц мест, но продукт — PWA для существующих пользователей; SEO-страницы можно добавить позже через пререндер.
- **Нет Prisma/Drizzle.** Supabase migrations — чистый SQL, который читаем и переносим. ORM добавил бы шаг генерации и разошёлся бы с RLS.
- **Нет React Query.** Данных мало, конфликтов мало; Zustand + собственный кэш проще и легче.
- **Платежей нет** — монетизация не входит в пилот.
